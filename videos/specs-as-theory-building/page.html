Specs as Theory Building

Peter Naur argued that the real product of programming is the theory in the programmers' heads. Now that agents write code from specs, his argument describes the job of whoever writes the spec.

This cut uses a local stand-in voice (Kokoro-82M) because no OpenRouter key was available when it was rendered. See About this cut.

The argument in four steps

  1. A program is a theory held by people

    For Naur, programming means building a theory, in the philosopher Gilbert Ryle's sense, of how part of the world will be handled by a program. Whoever holds it knows how the program works and can explain it, justify it and answer questions about it. The code and the documents, specifications included, are secondary products.

  2. Documents can't carry the theory

    In Naur's compiler case, a second team received full code, annotated listings, design notes and advice, and still proposed patches that would have wrecked the design. Theory passes between people who work together. When the team that holds it disperses, the program is dead, even if it keeps running.

  3. Agents make text nearly free

    Naur pointed out that the hope for cheap changes assumes text editing is the main cost, and he said that assumption is false. Agents cut the cost of producing text almost to zero. The expensive part, the theory, is still there.

  4. So specifying is where the theory gets built

    When agents write the code, the spec becomes the main thing people write. Writing it, by chasing down the rules, systems and stakeholders it depends on, is how a PM builds the theory. The agent receives the spec. The theory stays with the people who did that work.

Four habits for PMs writing specs

Each habit trains one of the abilities Naur says separate someone who holds a theory from someone who only has the documents.

  1. Trace every requirement to its source

    Naur: map

    Name the rule, the system and the owner behind each requirement, and list what is deliberately out of scope. Naur: deciding which parts of the world are relevant "can only be made by someone who understands the whole world."

  2. Write down the why, and what you rejected

    Naur: justify

    An agent can implement a list of requirements. It can't infer the reasons behind them. Record the reasoning and the alternatives you turned down, so reviewers and agents can check changes against intent.

  3. Rehearse change before sign-off

    Naur: adapt

    Run two or three likely changes through the spec, such as a new regulatory reading or a platform migration. If a change fits the existing design, the theory is sound. If it needs a patch, the theory has a gap.

  4. Sit with the people who hold the theory

    Keep it alive

    Shadow operations, sit with compliance, pair with platform engineers. Treat documents as evidence, not the theory. Then keep those people in the loop while agents build, because a program nobody can change intelligently is already dead.

<spec>             ::= <requirement> { <requirement> } <change-rehearsal>
<requirement>      ::= <what> <why> <source> { <rejected-option> }
<source>           ::= <rule> | <system> | <owner>
<change-rehearsal> ::= { <likely-change> "→" ( "fits" | "needs a patch" ) }

The same habits as a grammar, in Backus–Naur Form, the notation that carries Naur's name.

Naur, in his own words

"The proper, primary aim of programming is, not to produce programs, but to have the programmers build theories of the manner in which the problems at hand are solved by program execution."

Abstract, p. 253

"A person who has or possesses a theory in this sense knows how to do certain things and in addition can support the actual doing with explanations, justifications, and answers to queries, about the activity of concern."

§3, on Ryle's notion of theory, p. 255

"The theory built by the programmers has primacy over such other products as program texts, user documentation, and additional documentation such as specifications."

§4, pp. 255–256

"For this support to be valid it must clearly be assumed that the dominating cost is one of text manipulation. … On the Theory Building View this whole argument is false."

§5, on the cost of modifications, p. 257

"The death of a program happens when the programmer team possessing its theory is dissolved. A dead program may continue to be used for execution in a computer and to produce useful results."

§6, p. 258

"What is required is that the new programmer has the opportunity to work in close contact with the programmers who already possess the theory."

§6, p. 258

Peter Naur, "Programming as Theory Building," Microprocessing and Microprogramming 15 (1985): 253–261

Everything is generated from code: the script, word-aligned timing, hand-coded vector illustrations, a small SVG animation engine rendered frame by frame in headless Chromium, a procedural music bed, and sound effects placed on animation cues.

Voice. The pipeline synthesizes narration through OpenRouter's text-to-speech endpoint. The default is google/gemini-3.8-flash-tts with voice Charon. No OpenRouter key was available in the build environment, so this cut uses a local stand-in, hexgrad/Kokoro-82M (voice af_heart), the same model OpenRouter hosts as hexgrad/kokoro-82m. To re-render with an OpenRouter voice, set OPENROUTER_API_KEY and run ./build.sh. The animation re-times itself to the new narration.

Source. dudgeon/reqs-as-theory-building. It contains the script with page references, the storyboard, the render pipeline and the 1080p master.
